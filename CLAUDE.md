# DiagSpill Tracking — Claude Code Context

This repository contains a living tracking document for **DiagSpill**
(**CVE-2026-74469**), a **heap out-of-bounds write** in the Linux kernel's
**SCTP** stack, reachable through `sctp_diag`.  An SCTP association counts
its peer transports in a 16-bit `transport_count` (`sctp_assoc_add_peer()`,
`net/sctp/associola.c`); the 65,536th unique peer wraps it to zero.
`sctp_diag` then sizes the `INET_DIAG_PEERS` Netlink payload from the
wrapped count — reserving nothing — but still copies one `sockaddr_storage`
for every entry of `transport_addr_list`, spilling about **8 MiB** past the
skb tail (`inet_diag_msg_sctpaddrs_fill()`, `net/sctp/diag.c`).  Impact: a
kernel oops/panic (**DoS**) and, per the discoverer, **local privilege
escalation to root** via page-table grooming.

**Reaching the bug needs no privilege at all** — no unprivileged user
namespace and no capability — only that the **`sctp` and `sctp_diag`
modules are available**.  An unprivileged local user builds the oversized
association (via `connectx`, repeated ASCONF ADD-IP, or INIT address
parameters) and issues the diagnostic dump itself.  This is the single most
important thing about DiagSpill and what sets it apart from the three bugs
disclosed alongside it (see the sibling note below).

The canonical fix is [`bd0e9289e264`][fix] (*sctp: prevent peer transport
count overflow*), first released in **v7.2-rc6**.  **This is an ancient
bug, not a regression**: the reachable defect was introduced by
`8f840e47f190` (*sctp: add the sctp_diag.c file*) in **v4.7** (2016), so
**every maintained SCTP-capable kernel is in-window** — there is **no
"predates the introducing commit / not affected" case**, and no
`:heavy_minus_sign:` rows on age grounds.  A kernel is safe only by
carrying the fix.

**CVE-2026-74469** is assigned by the kernel CNA.  Discovered by Asim
Manizada (@manizada), who also authored the upstream fix, and disclosed
**2026-09-18** on oss-security.  PoC: <https://github.com/manizada/DiagSpill>.

**Companion trackers.**  DiagSpill is one of a **quartet** of local-root
bugs the same researcher disclosed on 2026-09-18; the other three are
tracked separately under their own nickname slugs:

- **DirtyAH6** (CVE-2026-80844, IPsec AH6/XFRM) — `~/src/dirtyah6`
- **TUNderflow** (CVE-2026-81000, TUN receive headroom) — `~/src/tunderflow`
- **PPPoEject** (CVE-2026-68121, PPPoE stale skb head) — `~/src/pppoeject`

They are different bugs in different subsystems with their own fixes and
first-fixed releases, so **keep their status out of this tracker** — cross-link
only (the *Related* Summary row, the commit-range closing sentence, and the
References rows).  DiagSpill is the reachability outlier: the other three
need unprivileged user namespaces or specific capabilities, DiagSpill needs
neither.

The rendered site is published at <https://kimmo.cloud/diagspill/>.

[fix]: https://github.com/torvalds/linux/commit/bd0e9289e2642f6a5c54faad304ce0f41e926d22

## What flips a verdict — the kernel backport, and only that

A row's verdict is one question: is the kernel inside the reachable window
(**4.7 through 7.1**) *and* missing the [`bd0e9289e264`][fix] backport?
A kernel outside the window, or carrying the backport, is not exploitable.
This is what *Status*, *First fixed*, and *Fixed since* key on.

The reachability gate is **module availability, not privilege**: the
`sctp` and `sctp_diag` modules must be loadable, and then any local account
reaches the bug.  This gate is recorded in prose and the Summary, **never**
as a table column, and it does **not** downgrade a verdict — an in-window,
unpatched kernel is `:x:` whether or not a given host blacklists `sctp`.
Two discriminators worth keeping straight in the prose, neither a column:

- **No privilege / userns gate.**  Unlike the three sibling bugs, DiagSpill
  needs no unprivileged user namespace and no capability.  Do not describe
  a user-namespace lockdown as a mitigation here; it does nothing.
- **Remote is DoS-only and off-default.**  A remote SCTP peer can drive the
  transport count over an association that negotiated ADD-IP, but only with
  ASCONF + SCTP-AUTH or `net.sctp.addip_noauth_enable=1` (both off by
  default) *and* something on the target issuing the diag dump.  No remote
  root.  The local, no-privilege path is the headline; keep the remote
  caveat proportionate.

The EL family blacklists `sctp` (and `sctp_diag`) by default via
`kernel-modules-extra`; that narrows *who* reaches an unpatched kernel but
never flips a verdict (an explicit `modprobe` still loads it).

The combined *Patch status* table is the **single source** for every
row's kernel versions, dates, and status — upstream and distros alike.
Columns: `Distribution | Release | Current kernel | First fixed | Fixed
since | Status`. The upstream kernel is the **first** "distribution" in
the table, labelled `Linux kernel`, one row per stable branch
(`mainline`, then the series descending); its upstream-specific prose
lives in the `### Linux kernel` subsection. Don't restate the table's
columns in prose or add a parallel per-release table. The version cells
hold versions only (or `:grey_question:` when unverified) — the verdict
lives in *Status* as the emoji **plus a one-word verdict** and an
optional short note after an em dash (`:white_check_mark: Fixed —
DLA-XXXX-1`, `:x: Vulnerable — no cherry-pick`); longer caveats go in
the `###` prose. Label opt-in/alternate kernel rows by their kernel
*series*, uniformly `<release> (<series> opt-in)` (`11 (6.1 opt-in)`,
`2023 (6.12 opt-in)`) — introduce the underlying package name
(`linux-6.1`, `kernel6.12`) in the `###` prose, never in the Release
cell. Row and list ordering: releases **descending** within
a distribution; within a release the default kernel row first, then
live opt-in/alternate series rows **ascending**, then superseded
(`old`) series rows **descending** — like releases, old series are
something users are expected to move up from. The same rule applies to
version lists in prose. Rows sharing a Distribution value must stay
contiguous — the browser transform renders each run as one group
heading row. Keep the `{.distros}` block attribute on the line
**immediately after** the table.

Amazon Linux ships **multiple kernel streams** per release (AL2023:
`kernel` 6.1, opt-in `kernel6.12`, `kernel6.18`). Give **each supported
stream its own row** — the default stream's row labelled `2023
(default)` (it is the plain `kernel` package — name that in the
`### Amazon Linux` prose, not the table), each opt-in stream by its
series (e.g. `2023 (6.12 opt-in)` — the `kernel6.12` package, named in
the prose): a narrow-window bug can leave the default stream
not-affected while an opt-in stream is affected (and separately
fixed), so a single AL row would hide or misstate it. Enumerate the
current streams from repodata at seed — include the not-affected ones
too, for a complete picture. (The skeleton table seeds today's streams;
adjust to whatever exists at seed.) **AL2 gets no rows**: it reached
end of support on 2026-06-30 with no further security updates for core
packages, so — like any release that was already EOL with no fix
expected before the tracker existed — it is covered collectively in the
`### Amazon Linux` prose (all streams vulnerable, no fix expected);
don't poll AL2 repodata.

Debian suites get one row for the **default** `linux` kernel and, where
one exists, a separate row per opt-in alternative kernel package (e.g.
bullseye's `linux-6.1` source package — the bookworm 6.1 kernel
rebuilt for bullseye, shipped via `bullseye-security` — as row
`11 (6.1 opt-in)`). A fixed opt-in row never flips the default row's
verdict: while
`src:linux` is open in the security tracker the default row stays
vulnerable. The same default-plus-variant row pattern applies to
Proxmox (`proxmox-kernel-*` series), with two wrinkles: a default row
is labelled plain `9 (default)` — its series is visible in *Current
kernel* and named in the prose — and there is a third Release label:
PVE opt-in kernels are previews of the next default (per the Proxmox
forum announcements), so series get superseded — a former default or
an opt-in overtaken by a newer one is labelled `old` (`9 (6.17 old)`).
Keep an `old` row (hosts still run it), but expect no more updates for
it: Proxmox discontinues updates for superseded series after a short
transition tail, and every such series is EOL on kernel.org, so a
vulnerable `old` row will likely never flip. **PVE 8** reached end of
life in 2026-08 with no further kernel updates: it keeps only its
frozen, already-fixed default row, its vulnerable `6.14` opt-in gets
no row (a short paragraph in the `### Proxmox VE` prose), and nothing new
is expected from the bookworm `pve-no-subscription` index or the
`bookworm-*` changelog branches. More generally, a release,
stream, or kernel series whose updates had already ended **before the
tracker existed** gets **no** row at all — `old`, opt-in, or
otherwise — if it died *without* the fix (the same principle as the
AL2 exclusion above): its permanent `:x:` verdict is one sentence in
the relevant `###` prose. A series that died already *fixed* may keep
its row — a frozen `:white_check_mark:` still answers a reader's
question. At seed, check when a candidate series last received an
update, not just whether hosts still run it. Don't add upstream
`Linux kernel` rows for series that appear in the table only because
PVE ships them — they are typically EOL upstream
without the fix, so such rows could never flip, and they would sit
misleadingly against PVE rows whose fixes arrive as cherry-picks; the
upstream-EOL fact is one sentence in the `### Proxmox VE` prose.
Niche variants
(e.g. the EL `kernel-rt` real-time kernel) get **no** row — cover them
as a reader-facing caveat in the family's `###` prose instead.

## Routine run scope — live Current kernel, sticky verdict columns

The **Current kernel** column is **live**: refresh it for **every** row
on every run — upstream point releases and distro package versions
alike — and record any movement. A Current-kernel bump alone is a real
content change: commit it and bump `lastmod`. The **verdict columns are
sticky**: *First fixed*, *Fixed since*, and *Status* change **only**
when a row actually flips — its kernel reaches a fixed upstream release
(see the `Linux kernel` rows), **or** the distro ships the
`bd0e9289e264` backport / cherry-pick. A Current-kernel bump that stays
in-window without the backport moves the *Current kernel* cell and
**nothing else**.

A distro flipping its **default kernel series** (e.g.
`proxmox-default-kernel` changing which series it depends on) is always
recordable: the default row keeps its plain `(default)` label while its
*Current kernel* moves to the new series, the superseded series gets an
`old` row of its own (re-sort: old rows follow the live opt-ins,
descending), a new opt-in series gets a **new row**, and the
verification log and prose are updated —
**together**; a log-only update leaves the tracker self-inconsistent. A
switch can also flip a verdict on its own, so re-derive the verdict
rather than carrying the old one across.

In the `Linux kernel` rows, *First fixed* is sticky — set once from the
`.dyad` when a branch first gains the backport, `—` while unfixed or
not affected — and gains a value only if a previously-unpatched branch
picks the fix up; *Fixed since* is the release tag date from
`~/src/linux/stable`.

`zcat` / `gunzip` **are** in the headless allowlist — use them for the
`Packages.gz` / repodata pulls — as are `grep`, `sort`, `rpmsort`,
`tail`, `jq`, `xq` and `tee`
(`tee` because a `>` redirection into the worktree is refused). Pull
only kernel versions and advisory state — the tracker records no other
per-distro facts.

**Live versions appear only in the *Patch status* table.** Never repeat
a row's *Current kernel* value (or any other value the routine run
refreshes) in the `###` prose or the verification log. Prose and log
name kernel *series/lines* (`the 6.12 line`) and sticky facts
(first-fixed versions, tag/ship/migration dates) only; a log entry
records the *source and method* for a live value (e.g. "*Current
kernel* read from BaseOS `primary.xml.gz`, highest `rel`"), never the
value itself. A sticky fact that happens to equal today's live value
stays — it is recorded for the event, not refreshed. A routine
Current-kernel bump then edits table cells (plus `lastmod`) and nothing
else.

**Never record NixOS channel git-revisions** (the
`channels.nixos.org/<channel>/git-revision` pins) in the tracker — they
advance on nearly every run.

## Conventions for status entries

A *Status* cell is the emoji plus its one-word verdict, optionally
followed by an em dash and a short note (advisory ID, `LTS`, `no
cherry-pick`) — longer caveats go in the `###` prose.  A note after the em dash must add
information the row's other columns do not: don't restate the verdict
(`Vulnerable — no fix yet` / `no backport yet` just repeats `Vulnerable`)
or the series already shown in *Current kernel* (`Vulnerable — 6.1 line` /
`no 6.1.y backport`).  A plain `:x: Vulnerable` is the norm; keep a note
only when it adds something — an awaited advisory (`no RHSA yet`,
`DSA-…`), a not-affected reason, a fix threshold or near-miss, or an
`LTS` marker on a fixed row:

- `:white_check_mark: Fixed` — the release's kernel carries the
  `bd0e9289e264` backport (confirmed, not merely announced): set *First
  fixed* to the first fixed build and set *Fixed since*.
- `:heavy_minus_sign: Not affected` — the release's kernel is outside the
  reachable window (predates the introducing commit); note the reason.
  Used for both `Linux kernel` rows and distro rows.
- `:x: Vulnerable` — an in-window kernel without the backport.
- `:warning: Staged` / `:warning: Mitigated` — not fully resolved: the
  fix is staged but not yet in the user-facing channel, **or** a distro
  default materially reduces impact; the word says which. A mitigation
  is **not** a fix — it never earns `:white_check_mark:`.
- `:grey_question: Unverified` — not yet verified.

### "First fixed" and "Fixed since" columns

Both are **sticky**, set when a row flips to fixed, and stay `—` while
the row is vulnerable, unverified, or not affected. *First fixed* is
the first release or package build carrying the fix — from the `.dyad`
for the `Linux kernel` rows, from the advisory / changelog for distro
rows. *Fixed since* is the date the fix first held: the release tag
date for `Linux kernel` rows, the advisory/ship date for distro rows
(see DESIGN.md for per-ecosystem derivations). Only touch either if the
verdict flips again or the recorded first-fixed build turns out to have
been wrong.

### Verification log

The section has a fixed shape: a short reader-facing intro paragraph
stays **visible**, and the log body is collapsed inside a
`{{< details summary="Full verification log" >}} … {{< /details >}}`
shortcode wrapper (rendered by
`site/layouts/shortcodes/details.html`). Keep the intro and the
wrapper intact. Inside the wrapper the
subsections are `####` headings (h4 — below the ToC's `endLevel`, so
the collapsed content has no ToC anchors pointing into it).

Log entries are **one top-level bullet per source or topic**, opening
with a terse bold lead and the method attribution (e.g. `**Debian**
(via …):`), followed by **one fact per nested sub-bullet** — never run
multiple facts together into a paragraph-bullet. Sub-bullets follow
the table's ordering conventions.

Update the section rather than appending a line per re-check. Edit the
relevant subsection in place — usually the one sub-bullet whose fact
changed. The log carries no dates of its own — the front-matter
`lastmod` is the document's only recency marker, so do not write
verification dates inline.

The log records **facts**, not run outcomes. Never write "no change",
"unchanged from prior run", "no verdict changes this run", or similar prose
anywhere in the tracker — an entry that is still accurate reports that by
staying untouched. This applies just as much on a run that *does* change
something real: update only the lines whose facts changed and leave every
other line exactly as it was.

### Date handling — first-seen / last-changed, not "today"

Dates in the prose are **first-seen / last-changed**, not "today". Only move
a date when the fact it qualifies changes. If the entire run is a no-op,
leave the file alone and don't commit — don't bump `lastmod`.

## Auto-update worktree

The auto-update job works in a dedicated git worktree
at `~/src/auto-update/diagspill`, checked out on a single long-lived branch
named `auto-update`. The wrapper merges `origin/main` forward into that
branch each run, then hands off to headless Claude, which commits any
changes back onto `auto-update` only — never a new branch, switch, push, or
PR. Merges of `auto-update` into `main` are manual.

One-time setup (from the primary checkout at `~/src/diagspill`):

```
git worktree add -b auto-update ~/src/auto-update/diagspill main
```

The wrapper runs `git fetch origin` and `git merge origin/main` under
`set -e`, so the repo needs a GitHub `origin` with `main` pushed or every
scheduled run aborts before doing anything. A freshly `git init`'d tracker
must `git remote add origin https://github.com/suominen/diagspill.git` and
`git push -u origin main` before the timer is worth enabling.

**The timer runs the wrapper from the primary checkout, not from the
worktree.**  `ExecStart` points at `<primary>/scripts/auto-update`, and the
wrapper reads its prompt from there too, so what executes is always code you
have reviewed and merged to `main`.  The agent can commit to `auto-update`,
so anything under `scripts/`, `.claude/`, `CLAUDE.md`, or `.mcp.json` on
that branch is untrusted: after merging `origin/main` forward the wrapper
refuses to run if any of them differs from `origin/main`, and it refuses
outright if it was invoked from inside the worktree at all.  A wrapper
change therefore takes effect on the next run after you merge it to `main`,
with no re-exec dance.

The service unit adds a kernel-level backstop — `ProtectSystem=strict` with
a short `ReadWritePaths` list (the worktree, the `.git` directories git has
to update, and `~/.claude/session-env`, which Claude Code writes on every
Bash call).  Without it the guards above are advisory: the agent may run
`curl`, and `curl -o` writes anywhere this user can, including over the
wrapper the timer runs.  Each repository's `.git/hooks` and `.git/config`
are handed back as `ReadOnlyPaths`, since nothing in a run needs to write
either and both are executable code.

A refusal is a stop-and-look rather than something to clear reflexively —
it means a file that should only ever arrive by merge was rewritten on the
branch.  Inspect it with `git -C ~/src/auto-update/<slug> diff origin/main
-- scripts .claude CLAUDE.md .mcp.json` before doing anything else.

To run a refresh immediately (same path the timer takes):

```
systemctl --user start diagspill-tracker-update.service
```

It is a `oneshot`, so the command blocks until the run finishes; follow its
output with `journalctl --user -u diagspill-tracker-update`. Run the trackers
**one at a time**, never in parallel — they share the reference clones
under `~/src`.

Wire the timer with relative symlinks:

```
ln -sr ~/src/diagspill/systemd/diagspill-tracker-update.service \
       ~/src/diagspill/systemd/diagspill-tracker-update.timer \
       ~/.config/systemd/user/
systemctl --user daemon-reload
systemctl --user enable --now diagspill-tracker-update.timer
```

The timer fires daily at `06:20` (mornings only: the one open axis,
Rocky, moves slowly) — pick a slot no other tracker uses
(verify the live set with `systemctl --user list-timers | grep tracker`,
not just the in-repo registry, which has gone stale) so the shared clones
are not fetched
simultaneously.

## Tearing down the auto-update

Unwire in this order — the sequence matters, because `systemctl disable`
needs the unit definition to still be resolvable when it runs.

1. `systemctl --user disable --now diagspill-tracker-update.timer` —
   because the unit definitions are symlinks, this also removes the
   timer's own symlink (systemd treats it as a linked unit).
2. `rm ~/.config/systemd/user/diagspill-tracker-update.service` (the
   `.timer` link is already gone after step 1).
3. `systemctl --user daemon-reload`
4. `systemctl --user reset-failed diagspill-tracker-update.timer` — the
   reload leaves the timer `failed (Result: resources)` ("Unit to
   trigger vanished") even in this order.

If the symlinks were removed *before* disabling, also delete the stale
`timers.target.wants/diagspill-tracker-update.timer` link before the
reload. Finally, from `~/src/diagspill`:
`git worktree remove ~/src/auto-update/diagspill` and
`git branch -d auto-update`.

## Local reference clones

git.kernel.org's cgit HTML pages and lore.kernel.org (the mailing-list
archive and its search) are Anubis-gated; WebFetch hits the no-JS
challenge, and headless curl gets a 403 or the honeypot page. Only the
git smart-HTTP protocol itself (`git fetch` / `git ls-remote`) is
ungated. The agent inspects kernel history via long-living local clones
under `~/src/linux/`:

| Clone path                       | Upstream                                                           |
|----------------------------------|--------------------------------------------------------------------|
| `~/src/linux/stable`             | `https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git` |
| `~/src/linux/net` | git://git.kernel.org/pub/scm/linux/kernel/git/netdev/net.git                                              |
| `~/src/linux/vulns`              | `https://git.kernel.org/pub/scm/linux/security/vulns.git`          |
| `~/src/proxmox/pve-kernel`       | `https://git.proxmox.com/git/pve-kernel.git`                       |

`net` is the maintainer tree where this subsystem's fixes
land (and get tagged for stable) before Linus. `vulns` is the kernel CNA's
CVE database. The wrapper refreshes the clones before invoking the agent;
inspect via the `origin/<branch>` remote-tracking refs.

**Is a stable branch fixed yet?**  The backport is a cherry-pick with a new
SHA, so search by upstream reference / subject:

```
git -C ~/src/linux/stable log v<series>..origin/linux-<series>.y --grep=bd0e9289e264 --grep='transport count overflow' --format='%h %s'
```

Keep the range bounded to `v<series>..` — an unbounded subject grep over
the whole branch history can match an ancient unrelated commit and read as
a false "fixed". **Check the subject of every hit**: a later commit that
cites bd0e9289e264 in its body or a `Fixes:` tag also matches the SHA grep,
and its backports can land in **later** point releases than the real
fix's — reading such a follow-up as the fix records first-fixed versions
too late. Only a hit with the fix's own subject is the backport; prefer
the `.dyad` (below) when it covers the branch.

## The CVE record (`vulns.git`)

**CVE-2026-74469** is assigned. The CNA keys each record on the *fixing commit
SHA*; the authoritative per-branch `<introduced>:<fixed>` versions are in
the `.dyad` (inspect via `origin/master`):

```
git -C ~/src/linux/vulns show origin/master:cve/published/2026/CVE-2026-74469.dyad
```

For a **kernel** CVE the Linux kernel is the CNA. A CVSS score usually
comes from Red Hat's security data or NVD, **not** from the kernel CNA
(only the `.cvss` file, when present, is the kernel CNA's own).
Attribute a score to its actual source in the Summary — "Red Hat", "NVD"
— never "the CNA", and record when NVD has published the record with no
score yet. Red Hat's own score may be marked `draft`.

## Distro kernel version sources

<!-- These recipes are bug-independent; keep them. Restrict to the distro
     rows you actually track, and use the ARCH that matches the bug. -->

- **Debian** — **the security tracker, not a madison base-version
  compare, is authoritative for Debian status.** Two traps make a naive
  version check wrong: the base suite lags the `-security` upload that
  ships the fix, and Debian often backports the fix to a version *below*
  the upstream first-fixed release — so comparing a base-suite version
  against the upstream first-fixed release can read an already-fixed suite
  as vulnerable.

  Read status and fixed version straight from the security tracker.
  WebFetch the human-readable per-CVE page, or `curl` the JSON and read the
  `CVE-2026-74469` block for each release's `status` (resolved/open) and the
  version under `repositories` (a `<suite>-security` entry means the fix
  shipped as a security update):

  ```
  curl -fsSL 'https://security-tracker.debian.org/tracker/data/json'
  ```

  Use the dak madison API only for the base-suite version and the
  sid/testing lineage (unstable=sid, testing=forky, stable=trixie,
  oldstable=bookworm, oldoldstable=bullseye):

  ```
  curl -fsSL 'https://api.ftp-master.debian.org/madison?package=linux&s=sid,forky,trixie,bookworm,bullseye&text=on'
  ```

  For a *Fixed since* date, use the `first_seen` of the fixed version in
  snapshot.debian.org:

  ```
  curl -fsSL 'https://snapshot.debian.org/mr/package/linux/<version>/srcfiles?fileinfo=1'
  ```
- **Proxmox VE** (x86-only; Ubuntu-derived): the `pve-no-subscription`
  `Packages.gz` (needs `zcat`) — *Current kernel* comes from **only** that
  apt index. The pve-kernel git changelog leads apt (git → pvetest →
  pve-no-subscription → enterprise), so use it only to confirm a
  cherry-pick, never as the version — mixing the two flips the version
  forth-and-back between runs; a cherry-pick in git not yet published to
  `pve-no-subscription` is `:warning: Staged`, not Fixed. A named
  cherry-pick is not the only fix path: for a series Ubuntu still
  maintains, the fix can arrive silently inside an `update sources to
  Ubuntu-<base>` rebase with no CVE-named changelog line, so compare the
  newest rebase base version against Ubuntu's fixed version for the
  series (`https://ubuntu.com/security/cves/CVE-2026-74469.json`, the
  `packages[].statuses[]` entries — `released` plus version); base ≥
  Ubuntu's fixed version means the PVE build carries the fix even with
  no cherry-pick line. ubuntu.com intermittently stalls for 20–30 s and
  then answers 504, so fetch with a per-attempt timeout and retries
  (`curl -fsSL --retry 4 --retry-all-errors --retry-delay 10 -m 45`)
  rather than giving up on the first error; the search endpoint
  `https://ubuntu.com/security/cves.json?q=CVE-2026-74469` returns the same
  record under `.cves[]` (select the exact `id`) as an alternate.
  Kernel.org EOL for the series proves nothing
  here — Ubuntu keeps fixing series long after upstream EOL; named
  cherry-picks are the signal only for series Ubuntu no longer fixes
  (superseded `old` series, and opt-ins whose Ubuntu HWE source is
  EOL). The default kernel *series* is whatever the
  highest-versioned `proxmox-default-kernel` meta-package depends on —
  re-check it each pull, it moves. Track `pve-no-subscription` only: the
  enterprise repo is HTTP-auth-gated (401 without subscription credentials)
  and receives the same kernels later. To confirm a security cherry-pick,
  read `debian/changelog` from the shared clone at
  `~/src/proxmox/pve-kernel` via its `origin/...` refs (the wrapper
  refreshes it each run — don't clone it per run, a clone made inside the
  worktree leaves untracked debris that stalls every later run).  Branches
  are named `<suite>-<series>` (`bookworm-6.8`, `trixie-6.17`) except the
  newest series on the current suite, which is `master` — don't assume a
  mapping, since PVE switches its default series mid-lifecycle and adds
  opt-in series.  Resolve the series from `proxmox-default-kernel` and the
  `proxmox-kernel-*` metapackages first, then pick the matching branch from
  `git -C ~/src/proxmox/pve-kernel branch -r` and confirm its changelog head
  names that series.  For an `old` row's series, refresh *Current kernel*
  from the same Packages.gz pull as the rest, but only re-read its
  changelog branch if that package version actually moved — Proxmox has
  stopped updating superseded series, so on a routine run there is
  nothing new to find there.
- **NixOS**: the channel kernel pin from `~/src/nixos/nixpkgs`
  (`kernels-org.json` at the channel's git-revision). The default
  `linuxPackages` is whatever `packageAliases.linux_default` points at in
  `pkgs/top-level/linux-kernels.nix` — read that alias, don't assume it is
  the newest or oldest LTS (it moves between releases). Never record channel
  git-revisions.
- **Rocky / RHEL**: Red Hat's security data is the authoritative
  leading signal for EL status — RHEL is upstream of Rocky and AlmaLinux, so
  neither can be fixed before RHEL is. curl
  `https://access.redhat.com/hydra/rest/securitydata/cve/CVE-2026-74469.json` and
  read the kernel `fix_state` (Affected / Not affected / Will not fix / Out
  of support scope) and `affected_release` (RHSA + fixed kernel NVR once a
  fix ships). If hydra 404s — it can lag a new record by days — read the
  CSAF/VEX record Red Hat publishes first:
  `https://security.access.redhat.com/data/csaf/v2/vex/<year>/<cve-id,
  lowercase>.json`, where `product_status.known_affected` /
  `known_not_affected` carry the per-product verdicts, `flags` the
  justification (e.g. `vulnerable_code_not_present`), and a shipped RHSA
  appears as a `vendor_fix` remediation with the fixed NVR. Never
  WebFetch the `access.redhat.com/security/cve/` page — it is
  JS-rendered and returns only the navigation shell headlessly, which
  reads as a false "no record". While `fix_state` is Affected with an
  empty `affected_release`, EL is unfixed. Confirm the Rocky ship via
  BaseOS repodata (`repomd.xml` → `*-primary.xml.gz`, needs `zcat`)
  reaching that
  NVR; AlmaLinux is the fastest rebuild (cross-check OSV
  `https://api.osv.dev/v1/vulns/CVE-2026-74469`). Red Hat also marks kernels that
  predate the bug **Not affected**, which confirms any pre-introduction EL
  rows.

  **Highest build: `rpmsort`, never `sort -V`.** Order the `kernel`
  `ver`/`rel` pairs from `primary.xml.gz` with `rpmsort` (Debian
  package `rpm`; allowlisted for the headless run), which applies
  RPM's own comparison — a numeric segment beats an alphabetic one, so
  `553.163.1.el8_10` sorts above `553.el8_10`, where a plain `sort -V`
  on the raw attribute puts EL8's base build on top. **Feed it real
  `kernel-<epoch>:<ver>-<rel>` strings.** `rpmsort` splits each line
  at its last two dashes and compares whatever precedes them as a
  package *name* with plain `strcmp`; only the version and release
  segments get RPM comparison. The raw `<version …/>` element has no
  dash, so the whole line is a "name" and sorts lexically: on live
  Rocky 8 `553.el8_10` lands last and `tail -1` returns the base
  build, and on AL2023 lexical order ranks `6.12.95` above `6.12.103`
  and `6.18.8` above `6.18.48`. A bare `ver-rel` is no safer: its
  `ver` becomes the "name", which is right only while every line
  shares one `ver` (`4.18.9-1.el8` sorts above `4.18.10-1.el8`). The
  epoch goes in front of the version because AL2023 has bumped it
  mid-stream (`kernel` and `kernel6.12` carry both `0` and `1`), and
  an epoch bump is allowed to reset `ver-rel`; `rpmvercmp` splits on
  `:` like on `.`, so `1:6.12.103` outranks `0:6.13.1`. Build the
  string with `jq` (allowlisted; a line without `epoch=`/`ver=`/`rel=`
  attributes emits nothing), order with `rpmsort`, take the last line
  (`rpmsort` has no reverse flag, hence `tail`, also allowlisted), and
  strip the `kernel-<epoch>:` prefix with `grep -o` so what is left
  is the `ver-rel` the version cells hold:

  ```
  curl -fsSL "${base}repodata/<hash>-primary.xml.gz" | zcat | grep -A2 '<name>kernel</name>' | grep -o '<version [^>]*>' | jq -R -r 'capture("epoch=\"(?<e>[^\"]+)\"") + capture("ver=\"(?<v>[^\"]+)\"") + capture("rel=\"(?<r>[^\"]+)\"") | "kernel-\(.e):\(.v)-\(.r)"' | rpmsort | tail -1 | grep -o '[^:][^:]*$'
  ```

  Take `<hash>-primary.xml.gz` from the `repomd.xml` href; AL2023's
  is the unhashed `repodata/primary.xml.gz`.

- **Amazon**: the machine-readable ALAS signal is the repodata
  **`updateinfo.xml.gz`** (maps CVE → ALAS → fixed kernel NVR) — the per-CVE
  ALAS HTML pages are JS-rendered and return nothing headlessly, so don't
  rely on them (reading them falsely sees "no advisory").  Resolve the
  mirror, fetch `<base>repodata/updateinfo.xml.gz` and pipe it through
  `zcat` into `scripts/alas-cve CVE-2026-74469` (below) for the ALAS id + fixed
  `kernel*` version; check **all** kernel streams (AL2023
  ships `kernel`, opt-in `kernel6.12`, `kernel6.18` — a narrow-window bug can
  leave the default not-affected but an opt-in stream affected/fixed).
  Current versions from `primary.xml.gz`, per stream, with the Rocky
  highest-build recipe above (`jq`-built `kernel-<epoch>:<ver>-<rel>`
  strings into `rpmsort`, never the raw element or `sort -V`; the
  epoch matters here, AL2023 has bumped it) and the stream's name in
  the `<name>` grep (`kernel`, `kernel6.12`, `kernel6.18`).
  **A CVE-grep miss can also
  mean the mapping is not published yet**, not that no fix exists: an
  ALAS lists only the CVEs known when it was issued, and amendments
  reach the repodata only when Amazon cuts the next immutable release
  snapshot — `mirrors/latest` moves in discrete jumps (for
  CVE-2026-64531 the cross-reference trailed the 2026-07-27 advisories
  by three weeks).  Amazon also backports fixes into builds *below* the
  series' upstream first-fixed release, so no version threshold can
  flip the row either.  When a kernel-stream security ALAS from around
  the disclosure window ships a build the stream has since adopted
  while the CVE grep still misses, look closer before recording "no
  ALAS".  **`updateinfo.xml` is not line-safe — never grep it by
  line:** it packs the tail of one `<update>` entry (references,
  pkglist) and the head of the next on a single physical line, so a
  line-oriented grep or awk pairs one advisory's CVE references with
  its neighbour's package list (the CVE-2026-68138 tracker missed its
  `kernel6.18` advisory for two weeks that way).  Use the
  `scripts/alas-cve` helper, which parses the XML and prints one
  tab-separated line per advisory and kernel stream — advisory id,
  issue date, severity, package, version-release — and exits 1 when no
  advisory names the CVE:

  ```
  curl -fsSL "${base}repodata/updateinfo.xml.gz" | zcat | ~/src/diagspill/scripts/alas-cve CVE-2026-74469
  ```

  Invoke it by that absolute primary-checkout path, as with every
  helper under `scripts/` (the worktree copy is untrusted and not
  allowlisted).  `-p <regex>` widens the package filter beyond the
  kernel stream packages.  Its tests live in `tests/` (`make check`).
  The same line-packing applies to `other.xml`, so a changelog
  attribution there needs an XML parse too (interactively, `python3`
  `xml.etree`; no helper covers it yet).
